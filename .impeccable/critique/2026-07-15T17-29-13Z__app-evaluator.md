## Anti-Patterns Verdict

**LLM assessment (A):** Mild slop, trending toward template. The workspace reads like a competent Shadcn/Tailwind admin scaffold — clean and functional but interchangeable with a thousand dashboards. Four-column stat-card row, repeating "white card + icon header" sections, search-toolbar + data-table: all well-worn shapes. Zero personality beyond DMW blue. Every page opens with the identical eyebrow/Georgia-h1/slate-subtitle cluster. Not ugly; not *designed* — defaulted.

**Deterministic scan (B):** Exit code 2. CLI found 2 "gray-on-color" warnings in `evaluator.css` (table header `th` muted-text on muted background — a minor contrast check, likely fine in both modes). B's manual scan over-reported 25+ hits; most are **false positives** I verified against source:
- *Gradient text* (claimed page.tsx:64): false — solid `text-[#093CA8]`, not `background-clip:text`.
- *Border-radius >16px* (8+ claimed): false — `rounded-lg` resolves to 4–8px via the token override, not >16px.
- *Decorative stripe* (amber banner, CSS vars): false — the amber block is a legitimate "Local export only" notice; the CSS-var line is just `:root` tokens.

**Real banned patterns B confirmed:** 3px amber top-border accent on the "Needs review" card (`border-t-[3px]`, side-stripe ban); 1px border + 24px-blur shadow on every card (ghost-card ban, `evaluator.css:12`); four identical icon+number stat cards (hero-metric / identical-grid cliché). Plus a genuine consistency gap: pages still use hard-coded `bg-white`/`slate-*` instead of semantic tokens, relying on `evaluator.css` overrides for dark mode — contradicting DESIGN.md's "use semantic tokens for every surface."

**Visual overlays:** Not available — no browser automation tool in this environment; live overlay/injection was not attempted.

## Overall Impression

Solid bones, defaulted skin. The decision state machine, dark-mode system, and mobile sidebar are genuinely well-built. But the surfaces are template-grade: identical cards, no queue workflow, two competing filter models, and no personality. The single biggest opportunity is to make the workspace a *queue*, not a dashboard — surface the next pending submission and let the evaluator move through it without navigating back to a list.

## What's Working

1. **Decision state machine is correct and guarded.** `DecisionControls` renders the right action set per status, disables reject when reason is empty, and uses an AlertDialog with destructive variant for high-stakes confirms. This is the best-designed interaction in the product.
2. **Dark mode is a real system.** `evaluator.css` overrides Tailwind utilities with CSS custom properties; `ThemeToggle` persists, uses `aria-pressed`, and avoids hydration flicker. Thorough work most Shadcn dashboards skip.
3. **Mobile sidebar is textbook.** Fixed drawer <760px with scrim, Escape-close, `aria-expanded`, reduced-motion aware. Login correctly suppresses the sidebar via `:has()`.

## Priority Issues

**[P0] Dead component shipped**
- *What:* `EvaluatorNav.tsx` is imported nowhere — a deprecated no-op in production.
- *Why:* Confuses contributors and signals sloppy housekeeping in a trust-sensitive product.
- *Fix:* Delete the file; grep to confirm no consumers.
- *Suggested command:* `audit`

**[P1] Two filtering architectures for the same data**
- *What:* Dashboard filters via URL params + server `getDashboard()` (full reload); Responses filters client-side via `useState`. Dashboard uses `<Link>` pills; Responses uses a `<select>`. Tables differ (6 vs 7 columns).
- *Why:* Switching pages breaks muscle memory; "Overview" looks like a subset of "Submissions" but isn't. Violates consistency, raises cognitive load.
- *Fix:* Unify on one filter model; standardize column set; add pagination if needed.
- *Suggested command:* `adapt`

**[P1] No "next pending" queue workflow**
- *What:* After a decision the evaluator stays on the detail page with no forward path; only "Resend receipt" (disabled for non-verified) remains. No count of remaining pending.
- *Why:* Core job is batch queue review; currently 3–4 manual navigations per decision, multiplied across dozens daily.
- *Fix:* Add "Next pending" CTA + remaining count after a decision; optionally auto-advance.
- *Suggested command:* `delight`

**[P2] Stat cards are non-actionable + banned patterns**
- *What:* Four identical stat cards; only "Needs review" differs via a near-invisible 3px amber top border (side-stripe ban). Every card pairs a 1px border with a 24px-blur shadow (ghost-card ban). None are clickable to filtered views.
- *Why:* Stat cards are expected shortcuts to filtered queues; the most actionable metric (pending) is the least differentiated. Two absolute bans are present.
- *Fix:* Make cards `<Link>`s to pre-filtered views; replace the 3px top stripe with a tinted background or left accent; drop the wide shadow (keep border or shadow, not both).
- *Suggested command:* `polish`

**[P2] Export field picker is developer-facing**
- *What:* 9 raw checkboxes, no select-all/clear, no grouping, labels are `full_name`-style strings with a buggy `replace("_"," ")` (only first underscore).
- *Why:* Evaluators can't quickly configure exports; raw field names are not user-facing.
- *Fix:* Human-readable labels (reuse the `download` labels map), add Select all / Clear, group fields.
- *Suggested command:* `clarify`

**[P3] Empty state uses a warning icon for a neutral condition**
- *What:* Zero-result filters show `AlertTriangle` ("No applications match these filters").
- *Why:* A warning icon for a neutral state desensitizes users to real warnings and can read as a system error.
- *Fix:* Use a neutral icon (`Inbox`/`SearchX`); reserve `AlertTriangle` for actual warnings.
- *Suggested command:* `quieter`

## Persona Red Flags

**Alex (Power User)** — batch-processes 20 pending submissions:
- No keyboard shortcuts (V/R/N); no bulk ops; no "next pending" — 80+ navigations for 20 reviews.
- Filter inconsistency blocks muscle memory (URL vs client state).
- `getAllSubmissions()` loads everything client-side; will degrade at scale.

**Sam (Accessibility-Dependent)** — keyboard/screen-reader review:
- Focus not returned to a meaningful target after AlertDialog closes.
- Table scroll region has `role="region"` + `tabIndex` but no scroll-state cue; more columns may be unknown to SR users.
- `evaluator.css:28` globally overrides `.uppercase { text-transform: none }`, silently defeating Tailwind `uppercase` everywhere — including table headers and the eyebrows (likely a bug).
- Remarks textarea has no visible char-count toward the 1000 limit.
- Dashboard filter pills (`<Link>` styled as buttons) lack `role="tab"`/`aria-selected`.

**Casey (Staff Reviewer Under Time Pressure)** — project-specific:
- No departure date in the table; no sort; no urgency indicator. Must open each submission to judge priority.
- Status badge shows raw `pending`/`verified` with no temporal context (today vs 3 weeks ago look identical).
- After deciding an urgent case, no path to the next urgent one.

## Minor Observations

- `evaluator.css:28` global `uppercase` override is almost certainly a bug — it defeats intended uppercase on headers/eyebrows.
- `border-t-[3px] border-t-amber-500` (Tailwind amber-500) conflicts with `.evaluator-page .border-t-[3px] { border-top-color: var(--warning) }` — two different ambers; intent unclear.
- Dashboard `getAllSubmissions()` fetches all rows just to count statuses — a server-side COUNT would scale better.
- Login `LoginForm` relies entirely on `evaluator.css` spacing; fields likely under-spaced.
- `back-public` link has no defined hover/focus state.
- Dark-mode card shadow uses `color-mix(... var(--foreground) 7% ...)`; in dark mode `--foreground` is near-white, so the "shadow" reads as a light glow (intentional per DESIGN.md, but unusual).

## Questions to Consider

1. If the evaluator's job is a queue, why is the queue not the first thing they see? What if the default view were "Next 10 pending, sorted by departure date"?
2. `getAllSubmissions()` runs on both pages. At what dataset size does this break, and is server pagination planned before then?
3. The eyebrow appears on every page with identical styling. If every page has one, does any? Should inner pages lean on the sidebar for context instead?
4. The decision panel is a 1/3 sidebar on desktop, stacked below on mobile. For the person making the decision, is that the *primary* element or a *secondary* one? Is the current layout right?
5. DESIGN.md promises "current state, next action, and reason without ceremony." Does the UI deliver "next action" and "reason," or only "current state"?
